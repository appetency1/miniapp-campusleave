## 一、项目概况

### 1.1 课题名称

**基于微信小程序的校园请假管理系统设计与实现**

该课题已作为当前毕业设计方向确定。选题时最重要的标准是：开发难度可控、容易完成、论文材料充分、答辩容易解释，不以追求复杂创新或堆叠技术为目标。

### 1.2 项目目标

实现一个供学生、辅导员/教师、管理员使用的校园请假管理系统，覆盖以下核心业务链路：

学生提交请假申请 → 辅导员审批 → 学生查看审批结果 → 请假期间管理 → 续假或销假 → 历史记录查询 → 管理统计。

系统同时支持两类请假：

- **离校请假**：学生离开校园，返校时进行定位校验销假；定位异常时允许申请人工核验。
- **校内请假**：学生在校园内因临时事务等原因请假，结束时由学生自主确认销假并记录操作时间。

### 1.3 当前技术路线

- 前端：微信小程序原生开发。
- 后端：Java + Spring Boot。
- 数据库：MySQL。
- 图表：可使用 ECharts 或适合小程序的图表方案。
- 文件：证明材料可先采用本地/服务器文件存储；具体部署方式待确定。
- 架构：前后端分离，采用常规分层架构，不引入微服务、工作流引擎等不必要的复杂技术。

### 1.4 设计原则

1. 先保证核心业务完整，再考虑视觉细节和扩展功能。
2. 业务规则必须先于页面、数据库和接口定稿。
3. 同一业务规则要在前端提示、后端校验、数据库约束和测试用例中保持一致。
4. 角色权限由后端强制检查，不能只靠前端隐藏按钮。
5. 重要业务操作留痕，不能随意覆盖历史记录。
6. 不为了显得“高级”而堆技术、堆页面、堆数据库表。
7. 项目资料区分“已确认”“暂定”“待确认”“不做”，避免把曾经讨论过的想法误当成最终决定。

## 二、当前决策状态

### 2.1 已确认的项目决定

| 项目 | 当前决定 |
|---|---|
| 课题名称 | 基于微信小程序的校园请假管理系统设计与实现 |
| 核心用户角色 | 学生、教师/辅导员、管理员 |
| 请假场景 | 同时支持离校请假和校内请假 |
| 审批规则 | 两种场景统一由辅导员审批 |
| 时间规则 | 允许跨天，结束时间必须晚于开始时间 |
| 校内销假 | 学生自主确认结束，记录操作时间 |
| 离校销假 | 返校时进行定位校验；定位异常允许人工核验 |
| 续假 | 与原请假申请关联，续假需重新审批 |
| 技术路线 | 微信小程序原生 + Java/Spring Boot + MySQL |
| 开发取向 | 以顺利完成毕设、易测试、易写论文和易答辩为优先 |
| 开发策略 | 按模块实现，逐步联调；优先保证核心链路可运行 |

### 2.2 当前方向，但不应过度扩展

- 学生端采用克制、清晰、具有一定产品辨识度的视觉设计。
- 曾讨论过以小熊/校园角色作为轻人格交互层，可通过表情和状态文案反馈审批、销假等结果；这不是核心业务，不应影响主流程开发。
- 学生端底部导航曾暂定为：首页、请假记录、消息、我的。最终应根据实际完成的功能确定，不能为了凑导航而做空页面。
- 教师端以审批工作台为主，强调待审批、申请详情、记录筛选与异常处理。
- 管理端主要负责账号、班级、辅导员负责范围、基础配置和统计。

### 2.3 尚未最终确定、开发前必须确认

1. **登录与身份绑定**：采用微信登录、账号密码登录，还是演示用账号登录。不要同时实现多套认证机制，除非学校明确要求。
2. **管理员范围**：管理员是否必须独立页面，还是先完成必要的账号、班级、教师关联及基础配置。
3. **证明材料规则**：哪些请假类型必须上传材料、允许哪些文件类型、文件大小上限。
4. **时间冲突规则**：当前建议同一学生所有有效申请统一检查时间重叠，包括离校和校内两类；需要在需求规格中正式确认。
5. **取消规则**：待审批时允许撤回；已通过但尚未开始时是否允许取消，以及是否需要原因，需明确。
6. **定位范围**：学校中心坐标、允许半径、定位异常的人工核验角色和处理步骤。
7. **逾期规则**：超过批准结束时间但尚未销假时，采用动态逾期标识，不建议把“逾期”混成永久业务状态。
8. **统计口径**：按申请数、已批准数、已销假数、逾期数等哪些指标统计；时间范围和状态口径必须一致。
9. **学校毕业设计要求**：论文模板、开题报告、任务书、中期检查、查重、答辩 PPT、提交格式与截止日期。当前资料未提供学校正式文件，必须以学院通知为准。

## 三、系统角色与权限

### 3.1 学生

- 登录系统并查看个人资料。
- 发起离校请假或校内请假。
- 填写请假类型、起止时间、理由和必要的补充信息。
- 按规则上传证明材料。
- 查看申请详情、审批进度和审批意见。
- 在允许的状态下撤回申请或取消尚未开始的请假。
- 对符合条件的申请发起续假。
- 离校请假：返校时发起定位校验销假；定位异常时申请人工核验。
- 校内请假：自主确认结束并记录操作时间。
- 查看历史记录和消息通知。

### 3.2 教师/辅导员

- 查看自己负责班级学生的申请。
- 查看待审批列表和申请详情。
- 批准或驳回申请；驳回必须填写原因。
- 审批续假申请。
- 查看请假记录并按学生、班级、时间、类型、场景和状态筛选。
- 处理定位异常人工核验。
- 查看逾期未销假记录。
- 只能查看和处理授权管理范围内的数据。

### 3.3 管理员

- 管理学生、教师和管理员账号。
- 维护班级信息。
- 配置辅导员与班级的对应关系。
- 维护必要的请假类型、证明材料规则和系统配置。
- 配置学校返校定位校验范围（如果定位功能纳入最终实现）。
- 查看系统统计数据。
- 不应在没有审计记录的情况下直接改写已完成的业务记录。

### 3.4 权限原则

- 学生只能操作自己的申请。
- 教师只能处理自己管理范围内的申请。
- 管理员负责系统基础数据和配置。
- 每次关键操作都由后端重新校验身份、权限、当前状态。
- 前端按钮显示与否只负责交互体验，不构成安全控制。

## 四、核心业务流程

### 4.1 学生提交请假申请

1. 学生进入申请页面。
2. 选择请假场景：离校请假或校内请假。
3. 选择请假类型，例如病假、事假、其他。
4. 填写开始时间、结束时间和请假理由。
5. 按场景填写补充信息。
   - 离校请假：可填写去向、联系电话等。
   - 校内请假：不显示离校去向和返校定位字段。
6. 按材料规则上传证明材料。
7. 确认信息并提交。
8. 后端校验时间、必填字段、申请冲突、用户身份和重复提交。
9. 校验通过后创建申请，状态进入“待审批”。
10. 系统记录提交时间，并向学生展示提交结果。

### 4.2 辅导员审批

1. 教师进入待审批工作台。
2. 系统仅展示其负责范围内的待审批申请。
3. 教师查看学生信息、请假场景、时间、理由、材料及相关记录。
4. 教师选择批准或驳回。
5. 驳回时必须填写原因。
6. 后端检查教师权限和申请当前状态。
7. 审批成功后记录审批人、审批时间、审批结果和意见。
8. 更新申请状态并通知学生。
9. 已被撤回、已被其他操作改变状态的申请，不得再次审批。

### 4.3 请假状态推进

- 审批通过后，如果尚未到开始时间，显示为“已通过/待开始”。
- 当前时间进入批准时间段后，可显示为“请假中”。
- 到达批准结束时间但尚未销假时，显示“待销假”或叠加“逾期”提示。
- 完成对应场景的销假后，进入“已销假”。
- “请假中”“待开始”“逾期”等部分状态可根据批准时间、当前时间和销假记录计算，不一定全部作为数据库永久状态保存。

### 4.4 离校请假销假

1. 学生在返校后主动点击“返校定位并销假”。
2. 小程序请求本次定位权限并获取位置。
3. 将本次定位结果与申请标识提交后端。
4. 后端检查申请属于本人、状态允许销假，并根据学校配置范围判断定位结果。
5. 定位符合范围：完成销假，记录销假时间和定位校验结果。
6. 定位失败、用户拒绝授权或定位在范围外：不直接完成销假，展示异常原因及重试/人工核验入口。
7. 人工核验通过后，由授权教师完成异常销假并记录核验人、时间和处理意见。
8. 只在销假时获取位置，不持续追踪学生。
9. 不应宣称定位能够绝对证明学生真实返校，也不应将定位失败直接认定为违规。

### 4.5 校内请假销假

1. 学生打开本人处于可结束状态的校内请假记录。
2. 点击“确认结束请假”。
3. 系统提示确认。
4. 后端校验申请归属和当前状态。
5. 确认后记录操作时间和操作人。
6. 状态更新为“已销假”。
7. 不要求进行返校定位校验。

### 4.6 续假

1. 只有已批准且尚未完成销假的申请可以发起续假。
2. 学生填写续假理由和新的结束时间。
3. 新结束时间必须晚于当前批准结束时间。
4. 后端创建与原申请关联的续假记录。
5. 续假由辅导员重新审批。
6. 续假获批后，才更新主申请的有效结束时间。
7. 续假被驳回时，原批准期限不变。
8. 续假审批期间，如果原批准期限已到，仍按原期限识别逾期风险，不能提前假定续假已获批。
9. 同一申请同时只允许存在一条待审批续假记录。

### 4.7 撤回与取消

建议的初版规则：

- 待审批：学生可以撤回，状态变为“已撤回”，并记录时间。
- 已通过但尚未开始：是否允许取消需在需求规格中确定；若允许，应记录取消时间和原因。
- 已进入请假中：不允许直接删除或改写原记录。若需要结束或延长，应走销假或续假流程。
- 已销假、已驳回、已撤回：原则上只能查看历史记录，不再执行原申请的审批操作。
- 所有关键操作都应检查当前状态，避免重复点击造成重复变更。

## 五、异常流程与业务规则

| 异常情况 | 建议处理 |
|---|---|
| 开始时间晚于或等于结束时间 | 禁止提交并提示修改 |
| 请假理由为空 | 禁止提交 |
| 必填材料缺失 | 禁止提交 |
| 同一学生存在时间重叠的有效申请 | 默认禁止提交并提示查看已有记录 |
| 两次申请仅时间相邻 | 可以允许，例如上一段 10:00 结束、下一段 10:00 开始 |
| 学生重复点击提交 | 后端防重复创建 |
| 网络异常后重试 | 不能重复生成申请 |
| 教师重复审批 | 只允许待审批状态执行一次 |
| 教师越权审批 | 后端拒绝 |
| 审批时申请状态已改变 | 不覆盖新状态，提示刷新 |
| 驳回但未填写原因 | 禁止提交审批结果 |
| 续假结束时间不晚于原结束时间 | 禁止提交 |
| 定位权限未授权或定位失败 | 提供重试或人工核验入口 |
| 定位超出学校范围 | 不自动销假，允许人工核验 |
| 超过结束时间仍未销假 | 显示逾期提示，提供续假或销假处理入口 |
| 续假未审批但原期限已到 | 原期限不变，继续按逾期规则处理 |
| 学生查看其他人的申请 | 后端拒绝 |
| 文件类型或大小不符合规则 | 上传前后均校验并给出提示 |

### 5.1 时间冲突判断

新申请与已有有效申请发生重叠的条件是：

`新申请开始时间 < 已有申请结束时间`

并且：

`新申请结束时间 > 已有申请开始时间`

两个条件同时满足，即判定为重叠。建议离校和校内申请统一检查，避免学生在同一时间段提交两种互相冲突的申请。该规则需作为正式业务规则确认。

### 5.2 逾期状态设计

不建议把“逾期未销假”设计成无法恢复的永久状态。更合理的做法是根据：

- 当前有效批准结束时间；
- 当前时间；
- 是否已销假；
- 是否存在已批准的续假；

动态判断是否逾期。续假获批后，系统按照新的有效结束时间重新判断。

### 5.3 定位隐私

- 仅在学生主动发起离校销假时请求定位。
- 只保存业务必要的校验结果、校验时间和处理记录。
- 是否保存精确经纬度，应按学校要求和数据最小化原则决定。
- 不做后台持续定位。
- 定位校验属于辅助核验，不等于绝对防作弊机制。

## 六、状态设计：开发前必须统一

### 6.1 建议区分三个维度

不要把请假场景、请假类型和业务状态塞进同一个字段。

- `leave_scene`：`OFF_CAMPUS`（离校）、`ON_CAMPUS`（校内）。
- `leave_type`：病假、事假、其他等。
- `status`：申请生命周期状态。

例如：一条申请可以是“离校请假 + 病假 + 请假中”。

### 6.2 建议的持久化状态

第一版可考虑：

- `PENDING`：待审批
- `APPROVED`：已通过
- `REJECTED`：已驳回
- `WITHDRAWN`：已撤回
- `CANCELLED`：已取消（若最终决定支持）
- `COMPLETED`：已销假

续假状态单独放在续假记录中：

- `PENDING`
- `APPROVED`
- `REJECTED`
- `WITHDRAWN`

“待开始”“请假中”“待销假”“逾期”等展示状态，可以由时间和记录计算，减少数据库状态之间互相矛盾的风险。

### 6.3 状态转换约束

- `PENDING` → `APPROVED` 或 `REJECTED` 或 `WITHDRAWN`
- `APPROVED` → `COMPLETED`；若尚未开始且允许取消，也可转为 `CANCELLED`
- `REJECTED`、`WITHDRAWN`、`CANCELLED`、`COMPLETED` 不允许再次走原申请审批
- 续假审批不应把原申请状态直接改成“续假审批中”后丢失原来的请假阶段；可以通过关联续假记录表达待审批状态，并在页面显示“续假审批中”。

具体枚举值可调整，但数据库、接口、前端文案、流程图和测试用例必须使用同一套规则。

## 七、数据库设计建议

### 7.1 设计原则

- 一张主表承载离校和校内两种申请。
- 续假独立记录，避免直接覆盖后无法追溯。
- 关键审批和销假操作留痕。
- 关系字段使用外键或明确的逻辑关联，并建立必要索引。
- 第一版不要为了“完整”而无差别创建大量表；每张表必须对应明确业务用途。
- 最终表结构以需求规格和状态机定稿后为准。

### 7.2 候选核心表

| 表名 | 用途 | 必要程度 |
|---|---|---|
| `user` | 登录账号、角色、账号状态 | 必需 |
| `student_profile` | 学生学号、姓名、班级等 | 必需 |
| `teacher_profile` | 教师/辅导员资料 | 建议 |
| `class_info` | 班级基础信息 | 建议 |
| `teacher_class` | 辅导员与班级对应关系 | 多班级管理时需要 |
| `leave_application` | 请假主记录 | 必需 |
| `leave_extension` | 续假申请及审批 | 若实现续假则必需 |
| `leave_approval_log` | 审批、撤回、取消等关键操作日志 | 建议 |
| `leave_material` | 证明材料元数据 | 若实现材料上传则需要 |
| `leave_checkin_log` | 销假、定位校验和异常核验记录 | 若实现定位/销假则需要 |
| `notification` | 审批结果、续假和销假消息 | 若实现站内消息则需要 |
| `system_config` | 定位范围等可配置参数 | 若需后台配置则需要 |

十二张表是候选完整设计，不代表必须全部在第一版实现。可合并或精简，但必须确保业务数据和关键历史记录不丢失。

### 7.3 核心表字段方向

#### `user`

- `id`
- `username` 或微信用户标识
- `password_hash`（仅账号密码登录时需要）
- `role`
- `status`
- `created_at`
- `updated_at`

微信登录和账号密码登录不必为了形式同时实现。最终选一种主要认证方式，并在论文中如实说明。

#### `student_profile`

- `id`
- `user_id`
- `student_no`
- `name`
- `class_id`
- `phone`
- `college`
- `major`

学院、专业等信息如果能从班级关联得到，可避免重复存储。

#### `teacher_class`

- `id`
- `teacher_id`
- `class_id`
- `created_at`

辅导员可以负责多个班级。审批时通过该关系校验教师的数据访问权限。

#### `leave_application`

建议包含：

- `id`
- `application_no`
- `student_id`
- `leave_scene`
- `leave_type`
- `start_time`
- `end_time`（当前有效批准结束时间）
- `reason`
- `destination`（可空）
- `contact_phone`（可空）
- `status`
- `approved_by`（可空）
- `approved_at`（可空）
- `created_at`
- `updated_at`

续假申请的目标结束时间应存放在续假记录中，审批通过后才更新主表的有效结束时间。不要在续假提交时提前覆盖原批准期限。

#### `leave_extension`

建议包含：

- `id`
- `application_id`
- `requested_end_time`
- `reason`
- `status`
- `reviewer_id`
- `reviewed_at`
- `review_comment`
- `created_at`

#### `leave_approval_log`

建议记录：

- `id`
- `application_id`
- `operator_id`
- `action`
- `old_status`
- `new_status`
- `comment`
- `created_at`

#### `leave_checkin_log`

建议记录：

- `id`
- `application_id`
- `operator_id`
- `checkin_type`
- `check_result`
- `exception_reason`
- `reviewer_id`
- `review_comment`
- `operated_at`

只有业务确有必要时才保存精确坐标。校内自主销假和离校定位销假应能区分。

### 7.4 主要关系

- 一个用户对应一个角色；学生或教师资料通过 `user_id` 关联账号。
- 一个班级有多名学生。
- 一个辅导员可以负责多个班级，通过 `teacher_class` 关联。
- 一个学生可以有多条请假申请。
- 一条请假申请可以关联多条续假记录，但同一时间最多一条待审批续假。
- 一条申请可以关联多条审批/操作日志、材料记录和销假校验记录。
- 消息记录关联接收用户，必要时关联申请。

### 7.5 数据一致性与安全检查

1. 申请编号唯一。
2. 学号唯一。
3. 用户角色与资料关系正确。
4. 防止重复提交和重复审批。
5. 续假审批通过与主申请结束时间更新应保证一致性。
6. 申请、续假和销假等关键操作应使用事务处理适当的多步数据库变更。
7. 教师越权访问必须在服务端拦截。
8. 重要历史业务记录不应随意物理删除。
9. 统计接口使用统一状态口径。
10. 为学生、状态、时间范围、班级等常见查询条件建立必要索引。

## 八、功能模块与页面范围

### 8.1 学生端

建议页面：

1. 登录/身份绑定。
2. 首页：时间信息、当前申请概况、申请入口、最近申请。
3. 选择请假场景。
4. 请假申请表单。
5. 提交确认/提交结果。
6. 请假记录列表。
7. 请假详情与审批意见。
8. 续假申请。
9. 离校定位销假。
10. 定位异常/人工核验申请。
11. 校内自主销假。
12. 消息通知。

首页不应诱导学生请假。没有请假记录是正常情况，显示中性空状态即可。产品角色或动画属于视觉增强，不应妨碍申请、审批、销假等核心操作。

### 8.2 教师端

建议页面：

1. 教师登录。
2. 待审批列表。
3. 申请详情与批准/驳回。
4. 续假审批。
5. 请假记录查询。
6. 逾期与定位异常列表。
7. 人工核验详情与处理。
8. 负责班级/学生信息查看。

### 8.3 管理端

建议页面：

1. 管理员登录。
2. 用户/角色管理。
3. 班级管理。
4. 辅导员与班级关系管理。
5. 请假类型/材料规则配置（如实现）。
6. 定位范围配置（如实现）。
7. 统计概览。

### 8.4 导航与页面原则

- 导航只保留真正有用途的一级模块。
- 页面数量不等于功能质量；避免重复页面。
- 学生端申请入口可以放在首页，不一定需要单独占据底部导航。
- 教师端以工作效率为主，不必强行使用学生端的吉祥物设计。
- 所有页面都应能追溯到明确的业务规则和验收用例。

## 九、建议开发顺序

不要同时生成所有代码。按以下顺序分阶段实现，每阶段完成后运行、验收，再进入下一阶段。

### 阶段 0：需求冻结与资料准备

产出：

- 需求规格说明书初稿。
- 角色权限表。
- 主业务流程图。
- 状态转换表。
- 异常处理规则。
- 数据库 ER 图初稿。
- 页面清单。
- 接口清单。

验收：离校、校内、审批、续假、销假、异常处理的规则没有明显冲突。

### 阶段 1：数据库与开发环境

1. 安装/配置 JDK、Maven、MySQL、微信开发者工具及 IDE。
2. 创建数据库和基础表。
3. 准备少量可重复使用的演示数据。
4. 明确配置文件、数据库连接和启动方式。
5. 确保后端能够启动并连接数据库。

验收：数据库初始化脚本可重复执行或有清晰的初始化说明；后端启动无关键错误。

### 阶段 2：后端基础框架

1. 统一响应结构和异常处理。
2. 实现登录与角色校验。
3. 实现基础用户/班级数据查询。
4. 实现分页、参数校验和必要日志。
5. 统一接口路径、请求字段和返回字段。

验收：接口可调用，非法参数、未登录和越权请求有明确响应。

### 阶段 3：请假核心链路

1. 学生提交申请。
2. 查询自己的申请列表与详情。
3. 教师查看待审批申请。
4. 教师批准/驳回。
5. 学生查看审批结果。
6. 申请状态正确更新并记录操作日志。

验收：使用真实数据库完成一次完整的“提交—审批—查看结果”流程。

### 阶段 4：销假与续假

1. 实现校内自主销假。
2. 实现离校定位获取和后端范围判断。
3. 实现定位失败、范围外、人工核验等异常路径。
4. 实现续假申请及审批。
5. 实现逾期标识和相关提醒。

验收：两种请假场景销假逻辑不同；续假获批前不会提前延长原期限；定位异常不会被直接标记为成功销假。

### 阶段 5：教师和管理员功能

1. 负责班级关系。
2. 教师数据范围权限。
3. 请假记录筛选。
4. 异常处理列表。
5. 必要的用户/班级/配置管理。
6. 统计接口。

验收：教师不能查看其他负责范围之外的申请；统计数据与实际记录一致。

### 阶段 6：小程序页面与接口联调

建议先做可交互 Demo，再接真实数据。页面实现按核心链路优先：

1. 登录。
2. 首页。
3. 申请表单。
4. 记录列表和详情。
5. 教师审批。
6. 销假与续假。
7. 管理和统计页面。
8. 消息与视觉增强。

验收：页面不只展示静态假数据；核心按钮能够调用接口并反映后端状态。

### 阶段 7：系统测试与修复

- 功能测试。
- 异常测试。
- 权限测试。
- 时间边界测试。
- 重复提交/重复审批测试。
- 数据一致性测试。
- 兼容性和页面交互检查。
- 修复后回归测试。

验收：核心用例全部通过；遗留问题有记录，不能在答辩中把未实现功能说成已实现。

### 阶段 8：论文、截图与答辩材料

1. 固定可演示版本。
2. 准备测试数据和演示账号。
3. 截取真实运行页面。
4. 整理架构图、流程图、ER 图和关键代码。
5. 完成论文各章节。
6. 制作答辩 PPT。
7. 编写演示脚本和问题清单。
8. 进行至少数轮从登录到销假的完整演练。

## 十、开发协作与每次任务的执行规范

后续使用 AI 辅助开发时，建议每个任务都遵循同一套流程：

1. 明确本次任务属于哪个模块。
2. 阅读相关需求、页面、接口和数据库文档。
3. 检查现有代码，不凭空重建项目。
4. 先说明计划修改的文件、接口、数据结构和影响范围。
5. 一次完成一个可验收的小任务。
6. 运行项目或执行对应测试。
7. 检查控制台、后端日志、数据库数据和页面结果。
8. 修复问题并进行回归测试。
9. 更新接口文档、测试用例或开发日志。
10. 记录当前已完成、未完成和下一步事项。

### 每个功能完成后的检查表

- [ ] 是否满足需求规格？
- [ ] 是否与已确认的业务规则一致？
- [ ] 前端校验和后端校验是否一致？
- [ ] 是否检查了身份、角色、数据范围和当前状态？
- [ ] 是否处理空值、非法参数、重复点击和网络失败？
- [ ] 数据库是否正确保存，是否有重复或矛盾记录？
- [ ] 页面成功、失败、加载中和空数据状态是否完整？
- [ ] 是否影响已有功能？
- [ ] 是否新增了不必要的依赖或复杂度？
- [ ] 是否有可复现的测试记录？

不要仅凭“代码生成完成”判断功能完成。必须有运行或测试证据。

## 十二、系统测试清单

建议把测试用例整理成独立表格，至少包含：用例编号、测试目标、前置条件、操作步骤、预期结果、实际结果、是否通过、备注。

### 12.1 正常流程

- [ ] 学生正常提交离校申请。
- [ ] 学生正常提交校内申请。
- [ ] 辅导员批准申请。
- [ ] 辅导员驳回并填写原因。
- [ ] 学生查看审批结果。
- [ ] 学生正常完成校内销假。
- [ ] 学生在范围内完成离校定位销假。
- [ ] 学生提交续假并获批。
- [ ] 教师查看负责班级的申请。
- [ ] 管理员维护班级和辅导员关系。
- [ ] 统计页面结果与数据库记录一致。

### 12.2 异常与边界

- [ ] 结束时间等于开始时间。
- [ ] 结束时间早于开始时间。
- [ ] 请假理由为空。
- [ ] 必填材料未上传。
- [ ] 时间段与已有有效申请重叠。
- [ ] 重复点击提交。
- [ ] 网络失败后重试。
- [ ] 已撤回申请再次审批。
- [ ] 两名教师/重复请求同时审批同一申请。
- [ ] 未授权教师访问申请。
- [ ] 学生访问他人申请。
- [ ] 续假时间不合法。
- [ ] 同一申请重复发起待审批续假。
- [ ] 续假驳回后原结束时间不变。
- [ ] 定位未授权、定位失败、范围外。
- [ ] 人工核验通过/驳回。
- [ ] 超过结束时间未销假。
- [ ] 校内请假销假不触发定位要求。
- [ ] 离校请假不能绕过定位/人工核验规则直接销假。
- [ ] 统计时间范围、状态筛选和总数口径正确。

### 12.3 测试数据原则

使用虚构的学生、教师、班级和申请数据。提前准备不同角色、不同状态、不同时间段的记录，保证演示时不会因没有数据而临时手工拼凑。

PPT 应服务于讲解，不应把论文大段文字直接贴上去。

### 13.3 现场演示顺序

建议演示一条完整主线：

1. 学生登录。
2. 创建一条离校请假申请。
3. 展示提交后的待审批状态。
4. 切换教师账号审批。
5. 回到学生端查看审批结果。
6. 演示离校定位校验销假；如果实际环境无法定位，使用已准备好的测试场景展示失败/人工核验流程。
7. 再简要展示校内请假和自主销假。
8. 展示续假、历史记录、统计或权限控制中的代表性功能。
9. 最后展示数据库或关键设计图。

演示前准备可复位的测试数据，确保账号密码正确、后端启动、数据库连接正常。不要在答辩现场临时修改数据库结构或现场生成大量代码。

### 13.4 常见答辩问题

**Q1：为什么选择这个课题？**  
从校园请假申请、审批、销假和记录查询的实际需求出发，说明课题适合用信息系统规范业务流程，并结合自己的实现范围说明选题价值。

**Q2：系统解决了什么问题？**  
说明统一申请入口、辅导员审批、状态跟踪、销假记录、历史查询和统计；不要夸大成已经解决所有校园管理问题。

**Q3：为什么采用微信小程序 + Spring Boot + MySQL？**  
从学生端使用便利、前后端职责清晰、关系型数据适合管理申请与审批记录、开发和部署难度可控等方面回答，并确保与实际实现一致。

**Q4：离校请假和校内请假有什么区别？**  
两者共享申请和审批主流程，但销假规则不同：离校请假需要返校定位校验，异常时可人工核验；校内请假由学生自主确认结束并记录操作时间。

**Q5：如何防止学生重复提交或重复审批？**  
说明后端对当前状态、时间冲突、重复请求进行校验；关键操作记录日志，并通过事务/约束保障数据一致性。只回答真实实现了的措施。

**Q6：如何防止教师越权查看学生申请？**  
说明后端根据教师与班级的关联关系检查数据范围，不依赖前端隐藏按钮。

**Q7：定位能否证明学生真实返校？**  
不能绝对证明。系统只在主动销假时获取定位，判断是否位于配置范围内；定位异常允许人工核验，定位结果是辅助核验依据而不是绝对证明。

**Q8：为什么续假要单独建表？**  
为了保存续假原因、目标结束时间、审批人、审批意见和处理时间，避免直接覆盖原结束时间后无法追溯。

**Q9：系统有哪些异常处理？**  
可回答无效时间、重复申请、重复审批、越权访问、续假驳回、定位失败、范围外和逾期未销假等；以实际测试结果为准。

**Q10：系统有什么不足？**  
可以诚实说明：目前定位校验仍可能受设备定位精度影响；系统尚未接入学校真实身份/教务数据；消息提醒、部署和高并发等能力可能有限。只能列出实际存在的不足，不能把未实现功能说成已经实现。

**Q11：系统的创新点是什么？**  
不要硬说算法创新。可以从面向校园请假生命周期的业务整合、区分离校与校内销假规则、异常处理和操作留痕等工程设计角度说明。是否符合学校对“创新点”的要求，应以导师意见为准。

**Q12：系统是否真正运行和测试过？**  
展示真实运行环境、测试数据、测试用例和结果。所有论文、PPT和口头陈述必须与实际完成度一致。

## 十四、现有方案审查：问题与风险

以下是对目前方案的审查，不代表这些问题已经全部解决。

### 问题 1：功能范围存在膨胀风险

当前讨论涉及两类请假、续假、定位、人工核验、消息、统计、用户管理、班级管理、材料上传和个性化角色。对毕业设计来说，功能并非越多越好。

**建议：**
- 先完成最小闭环：登录/角色 → 申请 → 审批 → 查看结果 → 销假 → 历史记录。
- 再补续假、定位异常和必要统计。
- 吉祥物、动画、复杂消息中心和非必要配置放在最后。
- 如果工期紧，优先保住业务完整性、论文证据和可演示性。

### 问题 2：登录和身份绑定方案未定

微信小程序并不意味着必须从第一天就实现完整微信开放平台登录。认证涉及开发者配置、身份映射和测试成本。

**建议：**尽早确定一种符合学校验收要求的认证方案，并让数据库、接口和演示账号保持一致。不要在临近答辩时再更换认证体系。

### 问题 3：定位功能是高风险实现点

定位权限、真机环境、学校范围配置、定位误差、隐私说明和异常处理都可能增加开发与测试工作量。

**建议：**尽早用真实设备验证定位接口。定位范围和人工核验规则必须明确；准备失败场景测试。不要将定位结果描述为绝对返校证明。

### 问题 4：状态可能设计得过多或互相冲突

“已通过、请假中、待销假、逾期、续假审批中”等状态若全部直接存进一个字段，容易出现状态不一致。

**建议：**将持久化业务状态与根据时间计算的展示状态分开；续假使用独立记录。先画出状态转换表，再实现代码。

### 问题 5：数据库候选表较多，存在过度设计风险

十二张表只是完整候选方案，不应未经论证全部实现。

**建议：**按实际功能逐张确认必要性。材料、通知、配置和日志表是否独立，取决于最终功能和追溯需求；但核心申请、续假和销假信息必须能被正确记录。

### 问题 6：材料规则尚未正式确定

前期提到病假材料可选/必填、事假不需要等示例，但还没有确认学校真实制度。

**建议：**在需求文档中把规则写成明确表格；如果无法获得学校制度，说明这是本系统采用的设计规则，不要声称是所有学校通用要求。

### 问题 7：统计指标容易口径不一致

例如“请假次数”究竟按申请数还是按获批数；“逾期数”是否包含正在审批的续假；“销假率”的分母是什么，都需要定义。

**建议：**每个统计指标都写清楚定义、筛选条件和时间范围，并用测试数据验证。

### 问题 8：前端页面、后端接口和论文可能不同步

如果先让 AI 生成大量页面，再临时改业务规则，会出现页面状态、数据库字段和论文流程图互相矛盾。

**建议：**先冻结核心需求、状态机和 ER 图；每次业务规则变化时同步更新接口、测试和论文相关材料。

### 问题 9：只展示页面、不验证真实业务，会影响答辩

静态页面看起来完整，不代表系统真正完成了业务闭环。

**建议：**每个核心功能必须有真实接口、数据库变化和测试用例。论文截图、测试结果和答辩演示必须来自实际运行版本。

### 问题 10：学校正式要求尚未纳入项目总纲

目前还没有在本项目资料中核实学校的论文模板、开题/中期节点、格式、查重与答辩要求。

**建议：**尽快取得学院正式通知与模板，优先级高于自行设计论文格式。学校规定与本文件不一致时，以学校规定为准。

## 十八、最终执行原则

这个项目最容易出问题的地方，不是某一段 Java 代码，而是**业务规则没定好就开始开发，开发后又不断改规则，最后页面、数据库、测试和论文各写各的**。

因此后续顺序固定为：

**确认规则 → 需求文档 → 流程与状态机 → 数据库设计 → 接口设计 → 分模块开发 → 联调测试 → 论文整理 → 答辩准备。**
